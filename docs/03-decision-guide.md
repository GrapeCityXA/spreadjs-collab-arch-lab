# 为自己的场景选一种模式

先从 `single` 跑通功能，再根据房间分布、负载和恢复要求决定是否增加节点。用户总数本身不足以决定架构。

## 先回答四个问题

1. 有多少人会同时编辑同一份文档？分别编辑不同文档的人，可以按房间分摊；同一文档里的所有人都要收到彼此的修改。
2. 每人多久编辑一次？1000 人偶尔查看和 1000 人频繁输入，服务负载不同。
3. 能否保证同一文档始终由同一个节点处理？能保证时可以评估 `sharded`；不能保证时需要考虑 `shared`。
4. 节点重启时允许中断多久，文档数据怎么恢复？这些要求需要存储、重连和运维流程共同实现。

## 按场景选择实验起点

| 场景 | 建议先试 | 重点观察 |
|---|---|---|
| 先把协同功能接进业务 | `single` | 同节点编辑是否正常，延迟是否符合需求 |
| 大量独立文档，每份文档人数较少 | `sharded` | 同房间是否始终落在同一节点，房间分配是否均匀 |
| 同一文档需要由多个节点服务 | `shared` | 跨节点消息、重新加入的数据、共享库并发写入 |
| 需要高可用、滚动更新 | 以 `shared` 为实验起点，另做故障测试 | 重连、未确认编辑、Redis 和数据库故障恢复 |
| 想测官方产品的容量 | 官方实现 + 独立压测环境 | 不能用 mirror 的性能代替 |

`shared` 提供跨节点协作所需的组件，并不等于完整高可用。Redis、文档库、入口都可能成为故障点；当前工程也没有完成生产级故障验证。

## 用一次小实验确认判断

先定义一个与你的业务相近、但规模较小的场景，例如 50 人、每 2 秒编辑一次、10 个房间：

```sh
npm run up -- --mode=sharded
npm run check
npm run bench -- --users=50 --interval=2 --duration=20 --rooms=10
npm run down
```

先确认检查项通过，再观察压测里的失败数、写入确认延迟和广播延迟。重复实验时保持参数、机器和软件版本一致，只改变你想比较的因素。

不要只看“最终数据相同”。实时消息可能已经断了，而重新加入时又从共享库读到了最新值。`broken-no-adapter` 就是为了演示这种情况。

## 增加节点能解决什么

- `sharded` 可以把不同房间分开，一个大房间仍受单节点限制。
- `shared` 可以把同一房间的连接和广播发送分散到多个节点，但总的接收人数没有减少。
- 同机增加进程仍共享 CPU、内存和网络，进程数不能等同于机器数。
- 改路由或增加节点不会自动迁移旧文档；尤其在 sharded 的节点本地存储场景，要先设计迁移和恢复。
