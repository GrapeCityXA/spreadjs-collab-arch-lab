# 在自己的环境中验证 SpreadJS 协同部署与负载

业务准备接入 SpreadJS 协同编辑时，常见的问题是：“我们的服务器够不够？用户增加后要怎么扩容？”只知道在线人数，很难回答这些问题。同样是 1000 人，分别编辑不同文档和集中编辑一份文档，产生的广播、文档状态与网络开销会相差很大。

[SpreadJS 协同架构实验室](../README.md)提供可运行的部署方案、同步检查和合成负载工具。客户可以在自己的机器与网络中做实验，把业务描述、实验报告和资源监控交给售前、售后共同分析，让配置讨论有具体依据。

**框架验证可以用 mirror；真实业务硬件评估必须用真实 SpreadJS 与官方协同链路。** 两者是不同实验，不能将 mirror 的吞吐、延迟或每格内存折算成官方硬件配置。下面的命令演示当前已有的 mirror 框架实验，真实业务的容量流程见后文，目前还需要补充相应压测能力。

## 什么时候可以用

| 你遇到的问题 | 可以怎样实验 |
|---|---|
| 不清楚选单节点还是多节点 | 先运行单节点基线，再用相同负载比较按文档分片等方案 |
| 多节点后有人收不到修改，刷新后却正常 | 检查房间路由、跨节点转发和共享存储，也可运行预设错误配置对照现象 |
| 想知道人数和编辑频率增加后会怎样 | 逐级施加 mirror 合成负载，记录成功写入、响应延迟、实际广播接收和各组件资源变化 |
| 售前售后难以复现客户现场表现 | 共同保存业务输入、版本、命令、报告与监控，比较相同条件下的结果 |
| 想确定真实业务需要什么硬件 | 先用本仓库验证部署与合成负载，再补充官方实现、业务工作簿和实际存储链路的容量测试 |

当前自动负载工具使用简化的 **mirror 实现**，模拟连接、单元格值修改、广播与状态共享。`check`、`bench`、`big-doc` 均针对 mirror；它们的数字不能直接换算成官方 SpreadJS 业务容量。官方实现需要相应授权，目前提供真实表格接入页面及两个浏览器互相修改少量单元格的同步测试。**仓库尚未提供真实工作簿装载与官方客户端业务压测器。**

`mirror` 指协同引擎，并不表示页面没有用 SpreadJS：默认 `/client/` 页面已使用真实 SpreadJS 表格控件，只是通过自定义协议同步简单值；`/official/` 配合 `--impl=real` 才接入官方协同客户端、服务端和 OT。`bench` 使用 Node 模拟客户端，不运行浏览器中的 SpreadJS 工作簿。

因此，当前可以获得“这个环境中的部署行为与合成负载表现”，并据此设计下一轮测试。要给出真实业务的最终硬件建议，还需完成下文的业务验证。

## 先把业务描述清楚

客户与售前售后先共同填写以下信息，完整模板见 [AI 硬件咨询模板](13-ai-hardware-sizing.md)。AI 可以帮助整理问题和核对计算，测量结果仍来自实际运行。

| 输入 | 需要说明什么 |
|---|---|
| 在线规模 | 同时打开的文档数、会话数、每份文档人数分布，是否有热点文档 |
| 文档样本 | 脱敏工作簿、有效单元格数量、公式与样式、图片和长文本、文件或快照大小 |
| 操作方式 | 每人多久操作一次，是否集中突发；改单格、粘贴多格、结构变化、导入导出分别占多少 |
| 保存与历史 | 保存指增量编辑还是整本上传；是否要求确认时已落库；快照频率、历史保留与备份策略 |
| 体验与恢复目标 | 编辑确认、其他人看到修改、首次打开的延迟目标；失败率；重连、故障与恢复要求 |
| 实验环境 | CPU 型号与 vCPU、内存、磁盘、网络、系统、Node 与依赖版本，各组件部署位置 |

验收目标需要双方事先约定。例如可以要求“在某个明确负载下，编辑确认 p95 不超过业务指定值”。延迟目标取决于业务体验需求，本仓库没有通用的达标阈值。

## 第一步：跑通框架部署与同步检查（mirror）

准备 Node.js 22 或 24 LTS 和 npm。下面的命令在工程根目录的 PowerShell 中执行；当前验证环境为 Windows + Node.js 24，macOS / Linux 尚未验证。

```sh
git clone https://github.com/GrapeCityXA/spreadjs-collab-arch-lab.git
cd spreadjs-collab-arch-lab
npm ci
npm run doctor
npm run up -- --mode=single
npm run check
npm run down
```

`doctor` 检查依赖、端口、Redis、浏览器与授权配置；它不会测出硬件容量。首次使用 `single`，无需 Redis 或商业授权码。在执行 `down` 前，也可打开[本机控制台](http://127.0.0.1:5173/)查看部署。

`check` 报告保存在 `reports/`。先确认同步检查符合预期，再增加负载；默认检查中的负载样本最多 300 个客户端，不能把模型中的人数当作实际接入人数。出现问题时，先看[第一次运行](01-quickstart.md)与[排障说明](08-troubleshooting.md)。

## 第二步：按一种业务分布验证框架负载（mirror）

假设先研究“每份文档 2 人，每人每 2 秒改一个单元格”的场景。下面三轮依次增加活跃文档数，保持每份文档人数和操作频率不变。

| 轮次 | 会话数 | 房间数 | 每房间人数 | 目标编辑数/秒 | 理论对端投递数/秒 |
|---|---:|---:|---:|---:|---:|
| A | 50 | 25 | 2 | 25 | 25 |
| B | 100 | 50 | 2 | 50 | 50 |
| C | 200 | 100 | 2 | 100 | 100 |

这些数字是场景计算，不是已测出的性能。每轮目标写入窗口为 120 秒，建连及最后一轮 ACK 收尾另计；为减少上一轮状态累积的影响，以下 mirror 实验在轮次之间重启服务。

```sh
npm run up -- --mode=single
npm run bench -- --users=50 --rooms=25 --interval=2 --duration=120
npm run down

npm run up -- --mode=single
npm run bench -- --users=100 --rooms=50 --interval=2 --duration=120
npm run down

npm run up -- --mode=single
npm run bench -- --users=200 --rooms=100 --interval=2 --duration=120
npm run down
```

`--interval` 和 `--duration` 单位为秒。`bench` 会把用户尽量均匀地分入房间，所有用户采用相同编辑间隔，每轮修改简单单元格值；它不会预先装载客户工作簿。每个生成器按同步波次发送操作，等待该轮全部 ACK 或超时后再进入下一轮，不模拟各用户独立到达的业务节奏。慢 ACK 也可能拖慢发送，即使生成器 CPU 尚未满。单次目标写入时长最多 600 秒，不能代替长时间稳定性测试。每轮从空的 mirror 状态开始，写入期间状态会增长；不同运行时长或预装载状态的结果要分别记录。

如果实际业务是“少数文档聚集很多人”，上面的分布就不合适。可先单独测试一个热点房间，例如保留用户数、把 `--rooms` 改为 `1`，并从较低人数开始。任意热点分布、不同文档规模占比和业务操作回放，目前需要扩展负载工具。

改变部署方案时，保留相同的负载参数。例如在 C 轮后比较本机三个分片进程：

```sh
npm run up -- --mode=sharded --nodes=3
npm run bench -- --users=200 --rooms=100 --interval=2 --duration=120
npm run down
```

这里是**同一台机器上的三个进程**，不会增加物理 CPU、内存或网络资源。`sharded` 按文档分摊负载，同一房间仍固定在一个节点，不能靠增加分片节点拆开热点文档。需要 Redis 的 `shared` 模式见[模式说明](02-modes.md)。真实多机实验见[多机操作手册](09-multi-machine.md)；当前跨主机 `shared` 存储尚未实现，多机编排的现有工程验证为同机 agent 模拟。

## 第三步：同时看报告和资源监控

`bench` 自动生成 `reports/bench-*.json`，终端会打印实际文件路径。保留每轮原始报告，并用操作系统、云平台或已有监控系统记录同一时间段内的资源变化。仓库目前没有自动生成 CPU、磁盘和网络的完整监控报告。

| 要核对的证据 | 如何理解 |
|---|---|
| 实际接入人数与 `roomDistribution.histogram` | A 轮应为 25 个两人房间，B 轮为 50 个，C 轮为 100 个；确认负载分布符合计划 |
| `targetOpsPerSecond`、`sentOpsPerSecond`、`targetRateAchievement` | 核对生成器是否达到计划发送速率；达成比 `1` 表示 100%，不是成功率 |
| `ops.ok`、`ops.failed`、`opsPerSecond` | 核对实际成功写入与失败，成功吞吐按写入窗口计算 |
| `ackMs`、`broadcastMs` 与样本数 | 分别表示编辑确认和接收广播的延迟；没有样本不能认为延迟为零 |
| `broadcastReceived` 与 `fanoutOps` | 前者是实际接收计数，后者根据写入与房间人数推算；两者不是同一种证据 |
| 服务端与生成器的 CPU、内存、GC、网络 | 判断资源是否持续增长、是否存在单进程瓶颈，以及生成器是否先达到上限 |
| Redis、数据库与历史存储的监控 | 测实际链路时核对延迟、磁盘读写、容量增长及网络，不能用本地 mirror 代替 |

连接阶段和写入阶段分开记录。ACK 是协议确认，是否包含耐久落库取决于实际实现；它不能自动代表业务保存完成。广播接收与写入的统计窗口不同，不要直接把两个速率相减当作丢失率；接收计数也不等于逐条去重后的完整性校验。多机广播延迟还依赖主机时钟，聚合分位数有特定口径，详见[性能与容量](05-performance.md#8-用你自己的场景测)。

可以用下面的表记录结果。表中没有预填性能值，实验后填写；资源按组件记录，避免只写一台机器的总 CPU。

| 记录项 | A 轮 | B 轮 | C 轮 |
|---|---|---|---|
| commit、Node/依赖版本、硬件与部署位置 | 待填 | 待填 | 待填 |
| 实际人数 / 房间分布 / 运行时长 | 待填 | 待填 | 待填 |
| 报告文件名 / 建连耗时 / 写入窗口 | 待填 | 待填 | 待填 |
| 目标发送率 / 实际发送率 / 成功写入率 | 待填 | 待填 | 待填 |
| 失败数 / ACK p95、p99 / 广播 p95、p99 与样本数 | 待填 | 待填 | 待填 |
| 各组件 CPU / 内存峰值与趋势 / 磁盘 / 网络 | 待填 | 待填 | 待填 |
| 是否满足本轮约定目标 / 异常现象 | 待填 | 待填 | 待填 |

`check` 的 `healthy` 表示检查覆盖的同步行为符合预期；`bench` 退出码为 0 表示该轮有成功写入、未报告写入失败且未取消。性能是否满足业务目标，需要结合上表判断。

## 从框架实验进入真实硬件评估

先找出是哪一部分开始不能满足目标，再改变配置重测。若发送率已经不足，同时生成器 CPU 很高，需要先确认生成器能力；也要检查是否有慢 ACK 拖住整轮发送。若发送率达到目标但延迟上升，应结合服务进程、网络和存储监控定位。CPU 总利用率低，也可能有单线程或热点文档排队。

框架实验先确认路由、转发、分布式生成器和报告流程可用，再进入官方链路的业务容量测试。以下选型判断必须使用官方链路实测：增加节点、提高单机规格、降低广播频率与调整文档分布，解决的问题不同；每次尽量只改变一个条件，用相同业务输入对比，避免把一次短跑的最大成功人数直接写成生产承载上限。

CPU 之外，还要分别计算全部活跃文档的内存、历史与备份的存储、稳态编辑和集中重连的网络，以及故障后剩余节点的余量。[候选容量账样例](12-scenario-assessment-saas-2000docs.md)展示了这些账如何一起算，其中的配置与倍率是带条件的候选，不是本轮实验结果。`capacity` 只是历史广播 CPU 系数的计算器；`big-doc` 只是 mirror 简单值状态的内存与快照探测，均不能代替真实工作簿测量。

## 真实业务硬件结论还需要哪些验证

在目标官方版本与客户环境中补充以下测试，才有足够依据收敛到业务硬件建议。资源监控、备份和故障演练可以使用客户已有平台。

1. **装载有代表性的真实状态。** 使用脱敏工作簿或协同快照，覆盖文档规模分布、公式、样式和图片；同时加载目标数量的活跃文档，测打开和重连。
2. **驱动真实业务操作。** 使用官方客户端复现修改、粘贴、结构变化及实际保存流程，覆盖热点房间、光标频率与突发负载；验证数据一致性。
3. **接入计划中的存储和历史链路。** 测量落库、快照、历史增长和恢复。本仓库没有生产 PostgreSQL 适配器，默认 mirror 本地状态退出后丢失。
4. **验证持续运行和故障余量。** 运行约定时长，模拟所需的节点或主机故障、重连和恢复，确认剩余资源仍满足延迟、失败率和恢复目标。

官方接入方法见[授权与官方实现](07-license.md)。其中的 `test:official` 是小规模浏览器同步验证，不能代替上面的容量测试。当前 `bench` 不能通过添加 `--impl=real` 变成官方业务压测。

## 客户与售前售后怎样协作

客户提供业务输入、脱敏样本和目标环境；双方约定实验负载及通过条件。实验后一起核对原始报告与组件监控，明确哪些配置已在什么条件下验证、哪些仍是假设，以及下一轮需要改变什么。

反馈问题时，附上工程 commit、系统与依赖版本、硬件和拓扑、完整复现命令、预期与实际现象，以及对应报告和监控时间段。涉及真实业务的样本通过约定渠道提供；公开 issue 前移除授权码、管理 token、凭据与真实业务内容。提交方法见[贡献指南](../CONTRIBUTING.md)。

硬件建议应写成“在这组版本、业务样本、负载、存储与故障条件下，这个候选满足了约定目标”，并保留证据。模型与示例的统一适用边界见[使用边界与免责声明](../DISCLAIMER.md)。
