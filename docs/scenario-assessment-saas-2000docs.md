# 场景评估：SaaS 云上 2 000 份文档 × 2 人 × 每 2 秒一次保存

> 这是一份**用本实验室的数据回答一个具体客户场景**的样例评估，不是产品承诺。
> 数据来源分三类：本机 `bench` / 客户端脚本实测（mirror 实现）、模型估算（历史系数）、工程假设，文中逐项标注。
> 客户口径已确认：文档规模 **1 万 / 10 万 / 50 万单元格，占比 60% / 35% / 5%**；每文档 2 人协同，每人每 2 秒保存一次；需要服务端持久化与历史版本恢复。

## 0. 结论摘要

| 结论 | 数值 |
|---|---|
| 并发编辑会话 | 4 000（2 000 文档 × 2 人），规划按 5 000 留重连/多标签余量 |
| 文档规模与数量 | 1 万格 × 1 200 份（60%）· 10 万格 × 700 份（35%）· 50 万格 × 100 份（5%） |
| 在线单元格总量 | **1.32 亿**（12 000 000 + 70 000 000 + 50 000 000） |
| 编辑速率 | **2 000 次/秒**（4 000 人 ÷ 2 秒） |
| 广播投递 | **2 000 条/秒**（同房间 2 人，每次编辑通知 1 个对端） |
| 模型 CPU（历史系数 12 700 条/秒/核） | **0.16 核**（开 presence 0.18 核） |
| 本机 mirror 实测 CPU | **0.25 核**（200 连接 / 1 738 op/s）～ **0.33 核**（4 000 连接 / 905 op/s） |
| 文档状态内存（mirror 实测 130–133 B/格稳态，峰值 283–490 B/格） | **≈ 17.2–17.6 GB**；按 200–300 B/格规划 **26–40 GB**；官方实现留 2–3× → **50–100 GB** |
| 单份文档内存（规划 250 B/格） | 10 万格 ≈ 25 MB · 50 万格 ≈ 125 MB |
| 一次保存的落库量 | 2 000 op/s × 0.2–2 KB ≈ **0.4–4 MB/s** |
| 50 万格文档的快照 | JSON ≈ 9.7 MB（19.4 B/格），压缩后约 2–4 MB，本机加入耗时 **2.0–2.5 秒** |

**一句话：这个场景 CPU 仍然极低，瓶颈变成了"文档状态常驻内存 + 历史版本存储 + 大文档加载延迟"。** 1.32 亿单元格按 mirror 稳态约 17.2–17.6 GB，但官方 OT 实现要保存更丰富的工作簿模型（值/样式/公式/历史），按 2–3× 预留即 **50–100 GB**；这决定了节点数量与单节点内存规格。

推荐生产形态：

| 组件 | 推荐配置（生产） | 数量 | 说明 |
|---|---|---|---|
| 协同节点 | **4 vCPU / 32 GiB** | **6 台**（3 AZ × 2，弹性 6→10） | 内存换机器：每节点承载 ~330 份文档、~15–25 GB 状态；CPU 每节点 < 1 核 |
| 负载均衡 / 网关 | 云 ALB（WebSocket + TLS + WAF）或 2 × nginx 2 vCPU/4 GiB | 2 AZ | `sharded` 按 `roomId` 一致性哈希；fd 上限调到 65 535 |
| PostgreSQL（持久化 + 历史元数据） | 8 vCPU / 32 GiB，主 + 同步备，NVMe ≥ 5 000 IOPS，PgBouncer | 2 | 批量提交 ≤ 500 事务/秒；200 GB 数据盘起 |
| 对象存储（快照 / 历史版本 / WAL 归档） | 标准存储 + 生命周期 | — | 首年 0.5–1 TB；按版本保留策略增长 |
| Redis（仅 shared 或路由表） | 2 vCPU / 4 GiB，主从 + Sentinel | 2 | 2 000 msg/s 不是容量问题 |
| 压测生成器（非生产） | 2 vCPU / 4 GiB | 3–4 台 | 单进程在 4 000 连接时只能发 ~900 op/s |

预算受限的替代形态：**4 ×（8 vCPU / 64 GiB）**，总内存相同、机器少两台，但单节点故障影响面更大，不推荐做 N+1 演练。
开发/测试环境按 1/3–1/2 缩容（§4.2）。

## 1. 场景输入与口径

### 1.1 输入

| 项 | 值 | 说明 |
|---|---|---|
| 部署 | 客户自有 SaaS 云 | 统一域名、多租户、横向扩容、高可用、备份恢复 |
| 环境 | 生产 / 开发 / 测试 | 三套隔离环境 |
| 同时在线编辑的文档 | 2 000 份 | 视为 2 000 个协同房间（room） |
| 文档规模分布 | 1 万 / 10 万 / 50 万单元格，60% / 35% / 5% | 即 1 200 / 700 / 100 份 |
| 每文档协同人数 | 2 人 | 每人 1 个会话；多标签/多设备会放大连接数 |
| 保存频率 | 每人每 2 秒一次 | 按"一次保存 = 一次单元格编辑操作"折算（见 §1.2） |
| 其他要求 | 服务端持久化、历史版本恢复 | 见 §6、§7 |

### 1.2 口径说明

1. **"50 万单元格"指单文档**，不是总量。三档文档合计 **1.32 亿**在线单元格，其中 5% 的大文档占了 **38%** 的单元格——**大文档是内存成本的主要来源**，不能按"平均 200 份/节点"去估算内存。
2. **"保存"按增量编辑理解**。本实验室的 `bench` 把一次操作当作一次单元格编辑（增量 op），这也是协同系统的真实数据单位。如果客户指"每 2 秒把整本工作簿快照写库"，2 000 次/秒 × 快照体积（10 万格 ≈ 2 MB、50 万格 ≈ 10 MB）会到 **GB/s 级**，任何数据库都不可行；必须"增量 op 持久化 + 定期快照"（§6）。
3. **历史版本恢复**按"可恢复到指定时间点/版本"设计：快照 + op 日志回放，而不是每次保存存一份全量（§7）。

## 2. 负载计算

### 2.1 会话、房间、速率

```text
并发会话      = 2 000 文档 × 2 人            = 4 000（规划 5 000）
编辑速率      = 4 000 人 ÷ 2 秒              = 2 000 op/s
每房间人数    = 2
广播投递      = 2 000 op/s × (2 − 1)         = 2 000 条/s
模型 CPU      = 2 000 ÷ 12 700               ≈ 0.16 核（presence ×1.17 = 0.18）
```

对照：本工程 `docs/05` 的历史数据里，"1 000 人同一份文档、每人 30 秒一次"就是 33 300 条/秒，约 2.6 核。
本场景只有它的 **6%**——每房间只有 2 人，扇出是 1 倍而不是 999 倍。**房间人数决定广播成本，文档规模决定内存成本，总人数不直接决定任何一项。**

### 2.2 内存：本场景真正的成本项

实测（§3）：mirror 稳态 **≈ 130–133 B/单元格**；按 200–300 B/格（含 GC 余量、官方实现更丰富的单元格模型）规划：

| 文档档位 | 数量 | 单元格总量 | 内存 @130 B/格（实测） | 内存 @250 B/格（规划） |
|---|---|---|---|---|
| 1 万格 | 1 200 份 | 1 200 万 | 1.6 GB | 3.0 GB |
| 10 万格 | 700 份 | 7 000 万 | 9.1 GB | 17.5 GB |
| 50 万格 | 100 份 | 5 000 万 | 6.5 GB | 12.5 GB |
| **合计** | **2 000 份** | **1.32 亿** | **≈ 17.2 GB** | **≈ 33 GB** |

- 官方实现（OT 历史、presence、更丰富的工作簿模型）按 **2–3×** 预留 → **66–99 GB**；再加 GC 与突发余量，规划 **90–150 GB 集群内存**。
- 单份文档：10 万格 ≈ 13–25 MB，50 万格 ≈ 67–125 MB。**一台 8 GiB 的节点装不下几份 50 万格文档**，这是节点规格从"4C8G"升到"4C32G"的原因。
- 连接本身很轻：4 000 连接稳态只占 15–40 MB，峰值 200–300 MB（§3 测试 A）。

### 2.3 网络与快照

| 项 | 估算 | 依据 |
|---|---|---|
| 增量保存流量 | 0.4–4 MB/s（2 000 op/s × 0.2–2 KB） | 假设，需按真实 op 体积校准 |
| 单文档快照体积 | 10 万格 ≈ 2 MB JSON / 50 万格 ≈ 9.7 MB JSON（19.4 B/格），压缩后约 1/2–1/3 | 实测（§3） |
| 4 000 个会话同时打开文档 | 快照总量 ≈ 2.6 GB JSON（2 000 份，压缩后约 0.9 GB），摊到数分钟 | 推算；50 万格文档单次加入 2–5 秒 |
| 打开 50 万格文档 | 单用户 2–5 秒加载（本机 2.0–2.5 秒） | 实测；跨地域会更高 |

> 带宽不是本场景的瓶颈（公网/内网都远低于 1 Gbps），**但"大文档首次加载/重连"是用户能感知的延迟项，要单独定 SLO**。

## 3. 本次补充实测（mirror 实现，本机，2026-10-28）

环境：Windows 22 核、Node 24、同一台机器同时跑服务端与负载生成器（数字偏乐观），实现为 `mirror`（零授权参考实现，单元格只存值，不含样式/公式）。

### 3.1 场景级负载（bench）

```bash
npm run up -- --mode=single --no-web
npm run bench -- --users=4000 --interval=2     --duration=15 --rooms=2000
npm run bench -- --users=500  --interval=0.05  --duration=20 --rooms=500
npm run bench -- --users=200  --interval=0.1   --duration=20 --rooms=100
npm run down
```

| # | 场景 | 连接 | 实测 op/s | 服务端 CPU | ACK p95 | 服务端内存 |
|---|---|---|---|---|---|---|
| A | 4 000 人 / 2 000 房间 / 每 2 秒 | 4 000 | 905（**生成器已饱和**） | 0.33 核 | 707 ms（排队造成） | 峰值 303 MB / GC 后 82 MB |
| B | 500 人 / 500 房间 / 每 50 ms | 500 | 5 512 | 0.58 核 | 61 ms | 12.4 万单元格 +26 MB |
| C | 200 人 / 100 房间 / 每 100 ms | 200 | 1 738 | **0.25 核** | 31 ms | 峰值 117 MB |

### 3.2 单文档 50 万单元格（`npm run big-doc`，mirror）

用 `scripts/big-doc.mjs` 向同一房间写入 500 000 个单元格，再让第二个客户端加入；服务端 RSS 从节点自己的 `/health` 读取：

```bash
npm run up -- --mode=single --no-web
npm run big-doc -- --cells=500000 --batch=200   # 写入 50 万格 + 第二个客户端加入
npm run down
```

| 指标 | 实测 |
|---|---|
| 写入 50 万格 | 46–47 秒，**10 600–10 800 op/s**（批并发 200） |
| 服务端 RSS（写入后立即） | 71 → 206–314 MB（283–490 B/格，含尚未回收的堆） |
| 服务端 RSS（空闲后稳态） | **136–138 MB → +65–67 MB ≈ 130–133 B/格** |
| 第二个客户端加入（全量快照） | 收到 500 000 格，耗时 **2.0–2.5 秒** |
| 快照 JSON | 9.3–9.7 MB（19.4 B/格），经协议压缩后传输 |

这条实测把"每文档 50 万格"从假设变成了可算的数：**稳态约 130 B/格；峰值按 300–500 B/格预留（GC 前）；快照 19.4 B/格、压缩后 2–4 MB、加入约 2 秒（本机）**。规划取 200–300 B/格，就是稳态与峰值之间的折中。

### 3.3 三条结论

1. **CPU 不是问题**：场景级负载 0.25–0.33 核；6 个节点分摊后每节点 < 0.1 核，买 4 vCPU 是为突发和 GC 留余量。
2. **内存是主要成本**：1.32 亿格 × 130–300 B ≈ 17–40 GB（mirror），官方实现 2–3× → **50–100 GB**，必须按"每节点 32 GiB"规划。
3. **生成器先饱和**：4 000 连接时单进程只能发 905 op/s，ACK 707 ms 是客户端排队而不是服务端慢。**验收必须多机分布式加压**。


## 4. 推荐硬件

### 4.1 生产环境（多租户、高可用、横向扩容）

| 组件 | 规格 | 数量 | 部署 | 依据与余量 |
|---|---|---|---|---|
| 协同节点 | **4 vCPU / 32 GiB** | **6**（3 AZ × 2，弹性 6→10） | 容器或虚拟机 | 每节点 ~330 份文档、~15–25 GB 状态（按官方 2–3× 预留）；CPU 每节点 < 1 核 |
| 负载均衡 | 云 ALB（WebSocket、TLS、WAF、连接数告警） | 托管，2 AZ | — | `sharded` 按 `roomId` 一致性哈希；`shared` 可最少连接 |
| PostgreSQL | 8 vCPU / 32 GiB，主 + 同步备，NVMe ≥ 5 000 IOPS | 2 | 跨 AZ，PgBouncer | 2 000 op/s 经批量提交后 ≤ 500 事务/秒；数据盘 200 GB 起 |
| 对象存储 | 标准存储 + 生命周期（快照/历史/WAL 归档） | — | 区域冗余 | 首年 0.5–1 TB，按版本保留策略增长（§7） |
| Redis | 2 vCPU / 4 GiB 主从 + Sentinel（或托管） | 2 | 跨 AZ | 2 000 msg/s 不是容量问题；HA 与低延迟是目的 |
| 监控/日志 | Prometheus + Grafana / 云监控 + 日志服务 | — | — | 每租户、每节点、每文档档位指标见 §8 |
| 压测生成器 | 2 vCPU / 4 GiB | 3–4 | 独立于生产 | 单进程饱和在 ~900 op/s（4 000 连接时） |

**为什么按内存而不是 CPU 配：** 目标负载的 CPU 只要不到 1 核，但文档状态要装 50–100 GB；按"4C8G × 3 台"配会在官方实现下内存不足。**6 ×（4 vCPU/32 GiB）= 192 GiB 总内存、24 vCPU**，是"内存够、CPU 不浪费"的形状；预算受限的替代是 **4 ×（8 vCPU/64 GiB）**。

**为什么 6 台而不是 1 台：** 除内存外，还要 ① 跨 AZ 的 N+1（一 AZ 故障仍有 4 台）；② 滚动发布逐台排空；③ 大文档（100 份 50 万格）在节点间均匀分布，避免单节点热点；④ 该场景 2 倍增长时直接加节点。

### 4.2 开发与测试环境

| 环境 | 配置 | 用途 |
|---|---|---|
| 测试/预发（staging） | 2 ×（4 vCPU/32 GiB，与生产同规格、数量减半）；Redis 1 ×（1 vCPU/2 GiB）；PostgreSQL 4 vCPU/16 GiB（可不做 HA）；同拓扑 + 同 LB 规则 | 发布演练、故障切换演练、按 1/3 负载（~700 文档 / 1 400 会话，含 50 万格文档）回归 |
| 开发（dev） | 1 ×（2 vCPU/8 GiB）节点 + Redis 容器 + PostgreSQL 容器（或镜像模式用本地 SQLite） | 功能开发；不承载容量结论 |
| 本地 | 单节点 + Redis 容器 | 与 `docs/01-quickstart.md` 相同 |

测试环境必须**拓扑一致**（多节点 + LB + Redis + PG），否则"测试通过、生产出问题"；但不需要生产级冗余，可以单 AZ、单 Redis、数据库不做 HA。**测试环境还要放一份 50 万格文档**，否则大文档路径永远没被验证过。

### 4.3 容量增长怎么扩

| 增长 | 动作 |
|---|---|
| 文档数 2 000 → 5 000（单元格 ≈ 3.3 亿） | 协同节点 6→10（按内存加），PG/对象存储扩容 |
| 每人保存频率 2 秒 → 0.5 秒（op/s ×4） | CPU 仍 < 1 核/节点；关注 PG 批量与 op 日志量 |
| 大文档占比 5% → 15% | 内存按比例涨（每 100 份 50 万格 ≈ +6.7–12.5 GB），先扩节点再加配额 |
| 单文档协同人数 2 → 20 | 广播成本 ×19，CPU 进入瓶颈，需重新评估架构 |

## 5. 架构选择：这个场景该用哪种

| | `sharded`（房间亲和） | `shared`（共享 room） |
|---|---|---|
| 消息路径 | 同房间必在同一节点，**跨节点转发 0** | 经 Redis 适配器转发 2 000 msg/s |
| 每节点 CPU | 更低（无转发） | 略高（实测仍 < 1 核） |
| 入口要求 | **必须按 roomId 做一致性哈希** | 任意节点即可，路由简单 |
| 横向扩容 | 加节点后部分房间需要重新路由 | 直接加节点 |
| 故障恢复 | 节点挂了 → 房间重路由 + 从 PG 重新装载（大文档重新装载需 2–5 秒） | 任意节点接管，客户端重连即可 |
| 依赖 | LB + 持久化文档库 | LB + Redis + 持久化文档库 |

**建议：sharded（房间亲和）+ PostgreSQL 持久化。** 理由：每文档只有 2 人，房间亲和没有任何代价，却省掉 Redis 转发；2 000 份文档分散到 6 个节点很均匀。
**什么时候改用 shared：** 运维上不想维护"房间路由 + 路由变化后的数据迁移"，或需要节点完全无状态——shared 用 Redis 换掉粘性路由，代价是 Redis 进入关键路径（本场景 Redis 负载极低，完全可行）。

两条路的共同点：**文档库必须独立于节点内存**（PostgreSQL）。本工程 `sharded` 默认 `store=local`（进程内存，重启即丢）只用于验证语义；生产必须换成可持久化、可跨节点读取的存储，"存储共享 + 传输分区"是合法组合。

## 6. 持久化与历史版本恢复

### 6.1 持久化设计

| 项 | 设计 | 量级 |
|---|---|---|
| 写入路径 | 每次保存 → 追加 op 记录（批量提交），异步确认 | 2 000 op/s，落库 0.4–4 MB/s |
| 批量 | 跨文档合并提交，目标 ≤ 500 事务/秒 | 2 000 op/s ÷ 4 = 500 |
| 快照 | 每文档每 5 分钟或每 N 次保存生成一次，写对象存储 | 全量快照集 ≈ 2.6 GB JSON / 0.9 GB 压缩 |
| RPO | 异步批量 ≤ 1 秒；关键租户可开同步确认（换延迟） | 单文档级 |
| RTO | 单文档恢复到任意时间点：秒级–分钟级（加载快照 + 回放 op） | 见 §7 |

### 6.2 历史版本存储

- **不按"每次保存一个版本"存**：2 000 保存/秒 × 30 天 = 52 亿个版本，不可维护。正确做法是 **快照 + op 日志回放**：任一时刻 = 最近快照 + 增量 op。
- 版本粒度建议：每 5 分钟或每 1 000 次保存一个"可恢复点"，用户侧表现为"可回到某时间点"。
- 存储量（按保留策略）：

| 数据 | 日增 | 保留 | 存储 |
|---|---|---|---|
| op 日志（压缩） | 17–52 GB/天 | 7 天热、90 天归档 | 0.1–0.5 TB 热 + 对象存储 |
| 快照（全量集，压缩后 ~0.9 GB） | 视快照频率 | 90 天 | 30–90 GB |
| 历史版本（按策略） | — | 90 天 | 0.1–0.5 TB |

结论：**对象存储 0.5–1 TB/年**、PG 数据盘 200 GB 起，配合生命周期与压缩即可；不要把 op 日志无限期留在 PG 里。

## 7. 高可用、备份与恢复

### 7.1 高可用

| 层 | 措施 | 目标 |
|---|---|---|
| 接入 | 多 AZ LB、健康检查、连接数/错误率告警 | 单 AZ 故障不断服 |
| 节点 | N+1、滚动更新、优雅排空（停止接新房间 → 落盘 → 移出 LB） | 发布不中断已有房间 |
| 客户端 | Socket.IO 自动重连 + 重连后从快照/OT 历史增量追平（大文档 2–5 秒） | 断线自动恢复 |
| Redis | Sentinel/托管主从自动切换；适配器断线重连 | 秒级切换 |
| PostgreSQL | 流复制 + 自动故障转移；连接池重试有上限 | 分钟级切换 |
| 演练 | 每季度一次"杀节点 / 杀 Redis / 切 PG 主 / 恢复单文档历史版本" | 有记录、可复现 |

优雅排空最容易漏：直接 kill 节点会丢未落盘编辑；正确顺序是**先摘流量、等房间空闲或超时、落盘、再下线**（本工程 `docs/09` 的 `down`/`detach` 演示了同样的顺序）。sharded 模式下节点恢复后要从 PG 重新装载文档，**50 万格文档重新装载需要 2–5 秒**，要纳入故障恢复 SLO。

### 7.2 备份与恢复

| 数据 | 备份方式 | RPO | RTO |
|---|---|---|---|
| 文档（权威数据） | PostgreSQL WAL 归档 + 每日全量；快照写对象存储 | ≤ 5 分钟（集群级） | 30–60 分钟（集群）/ 秒–分钟（单文档） |
| 历史版本 | 对象存储版本化 + 生命周期 | 按快照周期 | 分钟级 |
| 配置/密钥 | 密钥管理服务 + 版本化配置 | 变更即备份 | 分钟级 |
| Redis | **不作为系统记录，无需备份**（路由表可从一致性哈希重建） | — | — |

- 恢复演练比备份更重要：**每季度做一次真实恢复**（从 WAL 恢复到新实例 + 业务验证），并记录 RTO。
- 租户级导出/删除（GDPR 类要求）走对象存储与 PG 的 tenant_id 过滤，不依赖整库备份。

## 8. 多租户与统一域名

| 事项 | 做法 |
|---|---|
| 统一域名 | 一张通配符证书 + 一个 LB；按环境分子域（prod/staging/dev）；租户可用子域或路径前缀 |
| 租户隔离 | `tenant_id` 进入所有表与 roomId（如 `t:<tenant>:<doc>`），PG 行级安全（RLS）；查询与备份按租户可过滤 |
| 配额 | 每租户：最大并发会话、并发文档数、**单元格总量/大文档数**、op/s、单 op 体积、存储量；超限返回明确错误并告警 |
| 噪音邻居 | 网关限流 + 节点侧每租户连接/速率上限；大租户独享节点池（房间亲和天然支持"把某租户的房间哈希到专属节点组"） |
| 大文档公平性 | 50 万格文档的加载/快照会占用节点内存与 IO，按租户限制大文档数量，避免一个租户的 100 份大文档压垮单节点 |
| 观测 | 每租户：会话数、op/s、p95 ACK、失败率、断连率、**加载耗时**；每节点：CPU/RSS/连接数/事件循环延迟/文档数 |

## 9. 上线前验证计划（用本实验室 + 真实环境）

本实验室能验证**拓扑语义**（12 项检查）和 mirror 级别的负载行为；**官方 OT 实现的容量必须在客户环境用官方栈实测**。建议：

1. **语义先行**（1 小时）：`npm run up -- --mode=sharded --nodes=3` → `npm run check` → 确认 12 项（含房间亲和、跨节点行为、`load.scenario` 记录）。
2. **按目标场景压测**：多台主机分摊生成（本机 + 2 台 agent 起步，3 节点 = 本机 1 + 远端 2），打 4 000 会话 / 2 000 房间 / 每 2 秒 / 60 秒：
   ```bash
   # 主控；g1/g2 上先跑 npm run agent
   npm run up -- --mode=sharded --nodes=1 --agents=http://g1:9100,http://g2:9100 --agent-token=<token>
   npm run bench -- --users=4000 --interval=2 --duration=60 --rooms=2000 \
     --distribute=local,http://g1:9100,http://g2:9100
   ```
   注意：远端主机同时跑节点和生成器会抢 CPU；本机实测单进程在 4 000 连接时只能发 ~900 op/s，如果生成侧先饱和，再加 1–2 台只生成负载的主机。
   验收口径建议：成功率 ≥ 99.9%、ACK p95 < 300 ms、广播 p95 < 500 ms（跨 AZ）、每节点 CPU < 60%、24 小时内存无持续增长。
3. **大文档专项**：准备 10 万格与 50 万格的真实工作簿各一份，测量"首次打开 / 重连 / 从 PG 重新装载"的耗时与内存，确认 2–5 秒的加载延迟可接受，并观察快照对节点内存的瞬时冲击（本机写入 50 万格时 RSS 曾瞬时至 314 MB，GC 后回落）。
4. **阶梯加压**：500 → 2 000 → 4 000 → 5 000 会话；同时观察"打开的文档数 × 档位"对 RSS 的影响，找到内存拐点。
5. **历史版本恢复演练**：对同一文档制造 3 个版本，恢复中间版本，验证数据一致性与耗时。
6. **故障演练**：逐台杀节点、切 Redis、切 PG 主，记录恢复时间与是否丢编辑（对照 §7 的 RPO/RTO）；特别验证"大文档从 PG 重新装载"的恢复时间。
7. **官方实现容量**：官方 OT + presence 比 mirror 重（历史数据：presence 使投递 +17%、p95 +115 ms，且单元格模型更丰富），需在客户环境重测后再定最终规格。
