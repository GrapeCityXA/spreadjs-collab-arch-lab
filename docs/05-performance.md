# 性能与容量：先测自己的场景

设计客户现场实验、记录结果并与售前售后讨论配置，先看[客户环境容量实验指南](14-customer-sizing-guide.md)；具体负载命令见 [第 8 节](#8-用你自己的场景测)。需要 AI 帮你算硬件时，使用 [咨询输入模板与回答规则](13-ai-hardware-sizing.md)；完整的内存、保留策略和故障容量账见 [2 000 文档样例](12-scenario-assessment-saas-2000docs.md)。历史数字不能代替当前版本的测试。

**框架验证可以使用 mirror；真实业务的硬件评估必须使用真实 SpreadJS 与官方协同链路。** 下文 `check` / `bench` 的 mirror 结果用于检查框架与合成消息负载，不能用其吞吐、延迟或每格内存校准官方实现的硬件需求。应在目标官方版本、业务工作簿、操作负载和存储链路下测量各组件资源；当前仓库尚未提供这条路径的自动化容量压测器。

## 1. 先区分三类数字

| 数字来自哪里 | 能说明什么 |
|---|---|
| 本工程 `check` / `bench` 生成的报告 | 本次环境下 mirror 实现的行为和负载表现 |
| JSON 中保留的 `scenario.model.predictedCores`、`capacity` 输出 | 历史广播模型参考，程序没有测量本次 CPU；不是官方实现的硬件建议 |
| 历史官方实现的测试 | 当时版本、机器、网络和负载下的表现 |

本工程默认使用 mirror；它没有实现官方 OT 算法。历史数据来自官方 `js-collaboration` **19.1.4** 测试栈，当前工程声明的依赖为 **19.2.1 系列**，存储实现也不同。不要把两者的数字写成同一套测试结果。

原始历史产物不包含在本目录中，出处列在 [第 9 节](#9-数据出处)。未取得原始文件前，只能将下列数据视为维护者提供的历史记录，无法仅靠克隆本仓库独立复核。

## 2. 为什么只说“1000 人”不够

假设 1000 人在同一份文档里，每人每 30 秒改一次：

- 每秒大约有 33 次编辑；
- 每次编辑要通知另外 999 人；
- 合计每秒约 33 300 次消息投递。

如果每人改成每 2 秒编辑一次，投递量就增加到约 499 500 次/秒。如果这些人分别编辑互不相关的文档，投递量又会下降。

因此要一起记录用户数、房间数、编辑频率和操作内容。大文档、公式、导入导出、光标更新也会改变负载，本工程的单元格值演示没有覆盖所有真实工作簿操作。

## 3. 历史数据摘要

以下为官方 19.1.4 测试栈的历史记录，不是本轮审查重新测得的数据。

| 场景 | 历史结果 | 条件 |
|---|---|---|
| 1000 人加入同一小文档 | 加入 p95 25 ms，0 断连 | 同机，4 节点 |
| 1000 人，每人 30 秒编辑一次 | ACK p50 / p95 / p99 为 160 / 628 / 3735 ms；服务端合计 2.21 核 | 服务端、Redis、PostgreSQL、负载生成器全在同一台机器 |
| 相同人数和频率，关闭光标同步 | ACK p95 79.3 ms | 服务端与负载生成器分开，两台笔记本，有线千兆 |
| 相同人数和频率，每 5 次编辑同步一次光标 | ACK p95 193.8 ms；服务端合计 0.82 核 | 与上一行相同的跨机测试环境 |
| 400 人，每人 6 秒编辑一次 | 4 节点 p95 2969 ms；8 节点 p95 987 ms | 历史同机对比，总投递量相同 |

两组“1000 人 / 30 秒”数据不能平均，也不能解释成固定的容量区间。同机测试存在资源争抢，但测试窗口、负载进程数和光标设置也有差异，无法把差距全部归因于网络或单一组件。0.82 核、2.21 核都不是新部署的保证值。

历史光标同步对照中，p95 增加约 115 ms，投递量增加约 17%。这仅覆盖那次同步频率，不能直接套用到每秒刷新光标的场景。

## 4. 节点数与延迟

历史测试里，增加节点后延迟曾明显下降，但这不足以定义通用的“单进程广播上限”。同一张历史表里也存在投递更高、延迟反而更低的场景，说明操作内容、资源争抢和转发路径都需要一起考虑。

实际测试时应逐级增加负载，观察：

- 写入失败率和断连是否增加；
- ACK 与广播延迟的 p95 / p99 是否持续上升；
- 服务端、负载生成器、Redis、数据库和网卡分别是否饱和。

不要仅根据 CPU 没满就判断服务还有余量，单文档写入、单线程处理或队列也可能先限制吞吐。

## 5. 容量模型怎么理解

本工程在 [scenario.mjs](../src/lab/scenario.mjs) 中使用一个简化模型：

```text
U = 用户数，R = 房间数，t = 每人编辑间隔（秒）
q = floor(U / R)，r = U % R
r 个房间各 q+1 人，其余 R-r 个房间各 q 人
编辑次数/秒 = U / t
投递次数/秒 = [r × (q+1) × q + (R-r) × q × (q-1)] / t
预测 CPU 核数 ≈ 投递次数/秒 / 12700
```

这是人数**尽量均匀分配**且人人同频率时的精确投递计数；当前CLI/场景模型要求`1 ≤ R ≤ U`。例如 5 人分 2 房间是 3+2 人，每人 2 秒一次，投递为 (3×2+2×1)/2 = 4 次/秒；不能把两个房间都按 3 人计算。生成器分片可以没有某个全局房间的成员，但不改变全局R。真实分布应逐房间计算 `sum(该房间每秒编辑数 × (房间人数-1))`，热点不均匀时不能用均匀模型代替。

开启 presence 时，历史 CPU 估算另乘 1.17。这个系数来自特定光标频率的历史参考负载，并非当前程序采样得到的 CPU 使用率；真实光标消息频率和体积要单独记录。

**此模型只按广播投递估算 CPU，不是完整服务成本模型。** 1000 人各自编辑一份文档、每 2 秒一次，仍有 500 次编辑/秒，即使广播模型输出 0 核，也需要处理编辑、ACK、文档状态、持久化、快照和 GC。不能据此建议 0 CPU、0 内存或省掉服务器。

模型有助于比较场景量级。例如 1000 人同房间，30 秒一次约估算为 2.6 核；2 秒一次约 39 核。它不能据此决定采购多少服务器，还没有计入真实文档运算、故障余量和各组件容量。

## 6. 外推结果

| 场景，均为单房间 | 估算投递次数/秒 | 模型 CPU 核数 | 验证状态 |
|---|---|---|---|
| 1000 人 / 每 30 秒一次 | 33 300 | 约 2.6 | 有历史实测，环境不同 |
| 1000 人 / 每 15 秒一次 | 66 600 | 约 5.2 | 未实测 |
| 1000 人 / 每 6 秒一次 | 166 500 | 约 13.1 | 未实测 |
| 1000 人 / 每 2 秒一次 | 499 500 | 约 39.3 | 未实测 |

估算随编辑频率变化，不表示服务一定能达到该吞吐。热点文档串行写入、客户端处理和网络都可能先成为瓶颈。

## 7. 还没有验证什么

- 当前依赖版本的官方实现容量，以及它与 mirror 的性能差异。
- 超过 1000 人、复杂工作簿、大文档和长历史下的官方协同表现。
- TLS、跨地域网络、Redis 高可用和数据库故障切换。
- 本工程 agent 在真实多台主机上的完整部署与负载表现；现有验证使用同机进程模拟。
- 本工程的跨主机 shared 存储；当前只有 SQLite 文件演示，未接入 PostgreSQL。

历史官方工程有一次两台机器的有线测试，不等于本工程的多机功能已经在真实网络上验收。

## 8. 用你自己的场景测

本节命令验证 **mirror 框架与合成负载**。真实业务硬件测试须按上方要求另外接入官方链路；不要将以下步骤当作官方容量验收。

### 先跑小负载

```sh
npm run up -- --mode=single
npm run check
npm run bench -- --users=50 --interval=2 --duration=20 --rooms=1
npm run down
```

`check` 先验证同步行为。`bench` 持续施加负载，仅支持 mirror。首次不要直接运行数千人的场景，先确认负载生成器和服务器都有余量。

| 参数 | 含义 | check 默认 | bench 默认 |
|---|---|---|---|
| `--users` | 总用户数 | 20 | 50 |
| `--interval` | 每人每几秒编辑一次 | 2 | 0.6 |
| `--duration` | 负载持续几秒 | 8 | 20 |
| `--rooms` | 分到几个房间 | 1 | 1 |

需要毫秒精度时可用 `--interval-ms=500`。check 的负载样本默认上限为 300 人，超出时报告会标实际人数，完整场景仍只做模型估算。

### 看结果

- 成功 / 失败数：bench 退出 0 表示本次有成功写入、没有报告写入失败且未取消；有失败或没有成功写入时退出 1。这仍不代表性能达标，应继续检查延迟与样本数。
- ACK：从发出写入到服务端确认的时间。
- 广播到达：其他用户的修改抵达的时间；也要确认有足够样本。
- p95：95% 的样本延迟不超过这个值。p99 反映更慢的一部分请求。
- 节点分布：确认连接真的按所选模式分配。
- 投递量：报告中的 fan-out 根据成功写入数和观察到的房间人数推算，不是网卡抓包或完整收件确认计数。`broadcastReceived`才是实际收件样本计数，也要核对采样覆盖范围；`roomDistribution.histogram`记录人数分布。

吞吐分母必须注明窗口：分别记录建连/加入耗时、稳态写入窗口、该窗口内成功操作数，以及包含建连的总耗时。比较编辑能力时使用 `稳态成功操作数 / 稳态写入秒数`，同时检查目标速率与实际速率；总窗口吞吐另列，不能混用。旧报告若把建连计入分母，其较低 op/s 不能直接证明生成器或服务端饱和，也不能直接定位 ACK 排队发生在哪一端。无法还原窗口时标为“旧统计口径、需重测”，不要把它当作稳态容量。

新报告中`connectionMs`和`writingMs`分别记录建连与写入窗口；op/s按`writingMs`计算。`opsSent`是发送数，`sentOpsPerSecond`是写入窗口内发送率，`targetOpsPerSecond`是计划发送率，`targetRateAchievement`为实际/目标的比值；这些发送指标不等于成功写入率。验收还要看成功数、失败数、未完成请求与实际收件，不要只看目标达成比。

当前每个生成器按同步波次发送，每轮向所有用户发送一次操作，等待该轮全部 ACK 或超时，再补足剩余间隔。它不是各用户独立到达的负载；慢 ACK 可以拖慢整轮，即使生成器 CPU 未满也可能达不到计划发送率。`duration` 是目标写入时长，建连另计，最后一轮 ACK 收尾可能越过截止时间。

分布式广播延迟取各参与者分位数中的最大值，不是把所有原始样本重新计算的全局 p95。报告会标“多机取最差参与者”。

分布式写入在全部参与者ready后释放，连接保留至全部写完。广播接收使用ready至释放连接的独立窗口`receiveWindowMs`，覆盖开始信号时差与较慢写入者，接收率按此窗口计算；不能把它与写入窗口的推算投递率直接相减当作丢失率。ACK聚合合并每个参与者最多500条保留样本，只是这些样本的分位估计，并非全部操作按数量加权的全局分位数。

### 再逐步增大

保持操作和房间分布一致，逐级增加 users，或逐级缩短 interval。记录每轮的版本、配置、硬件、网络、失败率和延迟，并同时监控负载生成器。若它先饱和，测到的是生成器的上限。

需要拆到多台机器时，见 [多机手册](09-multi-machine.md)。sharded 的一个房间仍会固定在一个节点；增加 agent 不会把这个热点房间自动拆开。

### 只做计算

```sh
npm run capacity -- --users=1000 --interval=30000 --rooms=1
```

注意：capacity 的 `--interval` 单位是**毫秒**，与 check / bench 的秒不同。这是已有接口差异。输出里的核数和节点数都是估算，没有运行负载；每节点按几核除算，也不代表一个 Node 进程会用满这些核。
