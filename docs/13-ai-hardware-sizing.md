# 用 AI 做硬件咨询：输入、容量账与验证条件

把下面的模板连同本页、[性能与容量](05-performance.md)、[生产部署边界](06-production.md)交给 AI。带显式假设的例子见 [2 000 文档候选容量账](12-scenario-assessment-saas-2000docs.md)。本仓库是架构实验室，不是当前官方产品的硬件认证表。

使用模型、候选配置或 AI 回答前，了解[使用边界与免责声明](../DISCLAIMER.md)；回答仍需保留依据、假设和待验证条件。

**mirror 只用于框架与消息路径验证；硬件评估必须使用真实 SpreadJS 官方协同链路和业务负载实测。** AI 可以核算由业务输入确定的操作、投递、保留量和带假设的候选方案，不能用 mirror 的吞吐、延迟或每格内存折算官方容量，也不能把“已配置授权”当成“官方容量已测试”。

## 1. 可复制的咨询输入

```text
请基于本仓库文档评估协同服务硬件，先列缺失输入和已能确定的计算。
把回答分别标为：确定计算、历史/演示实测、工程假设、候选硬件、待验证。
给出 CPU/内存/磁盘/网络/台数及推导，不能把广播模型当完整容量模型。
mirror测量仅用于框架验证，不能折算成官方CPU/内存或推荐硬件；硬件实测须走真实SpreadJS官方链路。

版本和实现：官方 SDK/服务端版本=；mirror 或官方=；部署系统/云/地域=
在线文档数=；会话数（含多标签）=；房间人数分布（如1200份各2人、1份1000人）=
文档规模分布=；有效有值/公式/样式格数=；JSON/压缩后体积=；公式/样式/图片/导入导出情况=
编辑频率（每人/每房间、平均/峰值）=；一次操作影响格数及类型=；op平均/p95/最大字节数=
“保存”是增量op还是整本上传=；ACK是否必须在耐久落库后返回=
presence/光标频率、消息体积和订阅范围=
SLO：编辑ACK p95/p99=；广播p95/p99=；首次打开=；全量重连完成窗口=；失败率=
历史：op热保留天数=；归档总保留天数=；快照频率=；分层保留/对象版本策略=
RPO（允许丢多少已确认编辑）=；单文档恢复RTO=；整集群恢复RTO=
故障范围（单进程/单机/单AZ/整区域）=；故障期间是否同时滚动发布=；未来增长/预算=
已有实测：机器规格=；原始报告=；建连耗时=；稳态写入窗口和成功op数=；组件监控=
```

有效单元格指实际需要保存在模型中的数据/公式/样式等，不能把表格最大行列数直接当成内存格数。大范围样式、公式依赖、图片、长字符串及导入导出需要独立样本。未知字段保留“未知”，不要让 AI 代替用户编造。

## 2. 回答中的五类证据

| 类别 | 应该如何表达 |
|---|---|
| 确定计算 | 写出输入、公式、单位；输入改变即重算 |
| 历史/演示实测 | 写出版本、实现、机器、负载、窗口和出处；没有公开原始产物时说明无法独立复核 |
| 工程假设 | 写出取值范围及为什么需要它，例如系统预留、分布偏斜和压缩率；教学用峰值工作集必须标明任意假设，硬件判断要替换为官方实测H，不能设置mirror到官方的倍率 |
| 候选硬件 | 给出 CPU/内存/磁盘/网络/数量及适用条件；只在相应假设下成立，先租用或试验验证 |
| 待验证 | 给出真实官方栈、文档与持久化链路下的通过标准；未验证前不写“保证够用” |

不要把 mirror 实测、官方 19.1.4 历史数据与当前 19.2.1 系列依赖混成一套证据。`check=healthy`、`bench` 退出 0、预测核数低，都不是业务容量验收。

## 3. 一张能复核的容量账

| 项 | 计算与必须补齐的条件 |
|---|---|
| 编辑 | 每房间编辑率 `λ_i = sum(房间内各用户每秒操作数)`；全局 `sum(λ_i)`，另算峰值及批量格数 |
| 广播 | `sum(λ_i × (n_i-1))`；presence 另算。均匀分房时可用[商余数公式](05-performance.md#5-容量模型怎么理解) |
| CPU | 广播模型只说明广播量级；实测还要覆盖 OT、序列化、公式、TLS、持久化、GC、加载/重连和单文档串行瓶颈 |
| 文档内存 | 在真实官方协同与目标存储链路，同时装载全部目标工作簿和业务负载，测得峰值工作集H，覆盖历史、快照和GC；格数不足以确定H，shared 多副本须在实测部署中覆盖 |
| 故障内存 | `峰值工作集字节数 × 分布偏斜系数 / 存活节点数 ≤ 单节点GiB × 2^30 × (1-系统保留比例)`；先明确要承受哪种故障，GB需先乘10^9转为字节 |
| op存储 | 操作数/秒×实际存储字节/op×86400×保留天数；数据库行/索引、WAL、备份、临时空间与归档压缩分别计量 |
| 快照存储 | 全文档一套快照字节×每天套数×保留天数；分层策略各层相加，不能把日增当90天总量 |
| 稳态网络 | 增量上行、对端广播、ACK、数据库复制、Redis和快照写入分别算，避免只算单向 |
| 打开/重连网络 | 每个会话需要的快照字节求和×8/完成窗口秒数；文档只有一份，但两位用户可能都各收一份 |
| 台数 | 同时满足故障后的 CPU、内存、IO、带宽和热点约束；同机多进程不是多台高可用机器 |

容量用十进制 `KB/MB/GB/TB`；机器内存用 `GiB`（1 GiB = 2^30 B）。容量保留比例、负载偏斜与并发故障条件都要显式写出。

## 4. 四个常见问题应怎样回答

### 1000 人在线，每人 30 秒编辑一次，买什么？

先补房间人数分布、文档模型、存储/历史与可用性要求。确定编辑率为 33.33 op/s；若全在一份文档是 33 300 次投递/秒，若各自一份文档则没有对端广播，但有 1000 份状态。单房间历史广播模型约 2.62 核，presence历史系数下约 3.07 核，不能据此决定整套采购。

若需要立即启动验证，可租用一台 **8 vCPU / 32 GiB、100 GB SSD、1 Gbps 网络**的机器作为小工作簿试验候选；它没有生产高可用承诺。先测当前官方实现及真实工作簿；同文档多个进程分担广播要设计 shared 及存储，多核不等于单进程能用满。生产台数、数据库、磁盘和网络随输入重新计算。

### 2000 份文档，各2人，每人2秒保存一次？

会话数 4000、编辑率 2000 op/s、对端投递率 2000/s。文档为 1万/10万/50万格、占60%/35%/5%时，共1.32亿格。[样例](12-scenario-assessment-saas-2000docs.md)中的6×4 vCPU/64 GiB仅在独立、任意的H=99–148.5 GB教学假设下演示内存算术，非测得建议，不能据此推荐；官方H当前未测，必须用真实官方链路全量业务实测替换后重新选机器。也不能把0.16个广播模型核称作整套CPU需求。快照0.9 GB/5分钟、完整保留90天就是23.328 TB；op归档90天另有1.53–4.68 TB，均依赖另行声明的存储假设。

这里只适用于明确“各2人”的分布。只有4000会话和2000文档两个总数时，不能推断每份恰好2人；热点分布不同，广播量和单节点压力也不同，必须先问人数分布。

### 1000 人同一文档，每人2秒编辑，4核8GB可用吗？

不能从本仓库批准这个生产配置。500 op/s ×999 =499 500次投递/秒，历史广播模型约39.3核（presence历史系数下约46核），只是未实测的外推。若消息1 KB，仅广播载荷就约4 Gbps；8 GB是否够还取决于文档和历史。也不能由39.3直接采购40核：单文档串行写入、OT、客户端和网络都可能先受限，sharded加机器不能拆开这个房间。应先验证官方栈的单文档扩展能力、实际光标频率和延迟SLO。

### 1000 人各自一文档，每人2秒编辑，是不是不需要CPU和内存？

仍有500 op/s。广播模型0核只表示没有其他协作者接收广播；连接、编辑、ACK、状态、持久化、快照与GC仍然消耗资源。1000份各10万有效格合计1亿格，但格数不足以确定内存；必须在真实官方协同和目标存储链路，同时装载全部目标工作簿与业务负载，测得峰值工作集H。可按文档分片组织验证，具体机器仍要用完整容量账和官方实测确定。

## 5. 何时能把候选变为采购建议

必须在目标官方版本、真实工作簿和目标持久化/历史链路上同时加载全部目标状态与操作。先完成建连，再统计稳态操作数和延迟，同时监控生成器与各组件；不能把含建连的旧总窗口op/s当作稳态上限。进行长时间测试、快照并发、全量重连及指定故障范围的恢复演练，证明存活节点仍满足容量公式与业务SLO。原始报告应包含配置、窗口、样本量、丢失/重复编辑检查和恢复结果。

本仓库当前没有生产PostgreSQL适配器，真实跨主机、TLS与HA仍需验证。当前能直接生成的mirror报告只能帮助检查拓扑和演示负载；官方实现的容量验证需要额外负载方案，见[授权与官方实现](07-license.md)。
