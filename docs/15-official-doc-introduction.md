# 在客户环境中实验，为协同硬件选型提供依据

接入 SpreadJS 协同编辑时，服务器该配多少核、多少内存，需要几台机器？只看在线人数很难回答。1000 人集中编辑一份文档，与分散编辑 1000 份文档，广播量和文档状态占用不同；编辑频率、工作簿复杂度、历史保留与故障恢复要求，也会影响配置。

开源的 [SpreadJS 协同架构实验室](../README.md)提供可运行的部署方案、同步检查和合成负载工具。客户可以在目标机器与网络中实验，保存业务输入、报告和资源监控，与售前、售后一起分析瓶颈，比较硬件候选，确定下一轮需要验证什么。

**框架验证可用 mirror；真实业务的硬件评估必须使用真实 SpreadJS、官方协同客户端与服务端、业务工作簿及操作负载。** mirror 的吞吐、延迟和每格内存不能换算成官方实现的硬件配置。

## 可以用来做什么

工程提供单节点、按文档分片、同房间跨节点三种部署方式，以及预设错误配置。你可以先确认两个页面是否同步，再逐步增加会话和文档数，观察编辑确认、广播接收及资源变化；也可以对照“刷新后正确、编辑时不同步”等现象排查路由、转发和存储。默认多节点是在同机运行多个进程，不会增加物理资源。

## 先完成一轮框架实验（mirror）

准备 Node.js 22 或 24 LTS、npm 及 Git，在 PowerShell 中执行以下命令。当前已在 Windows + Node.js 24 上验证，macOS、Linux 尚未验证。首次使用默认 `single` 模式，不需要 Redis 或商业授权码。

```powershell
git clone https://github.com/GrapeCityXA/spreadjs-collab-arch-lab.git
cd spreadjs-collab-arch-lab
npm ci
npm run doctor
npm run up -- --mode=single
npm run check
npm run bench -- --users=50 --rooms=25 --interval=2 --duration=60
npm run down
```

这一轮计划让 50 个会话分入 25 个文档房间，每份 2 人、每人每 2 秒修改一次简单单元格值，目标编辑率为 25 次/秒。60 秒是目标写入窗口，建连和最后一轮确认收尾另计。报告保存在 `reports/`；同时用系统或云平台监控分别记录服务端与生成器的 CPU、内存、磁盘和网络。

检查通过后，再保持操作类型和分布一致，逐级增加负载。核对实际发送率、成功写入、延迟与样本量，再结合监控判断哪一部分受限。`healthy` 或压测退出码 0 都不表示业务容量已经达标。详细步骤见[客户环境实验指南](14-customer-sizing-guide.md)，输入整理见[硬件咨询模板](13-ai-hardware-sizing.md)，报告口径见[性能与容量](05-performance.md)。

## 再用官方链路评估业务硬件

默认工具使用简化的 `mirror` 实现，模拟连接、值修改、广播和状态共享；不会预装客户工作簿，也没有官方 OT 算法。其结果适合研究架构与合成负载，不能直接换算成真实 SpreadJS 容量。官方实现需相应授权，工程已有接入页面和小规模浏览器同步功能测试；这些测试不等于容量验证，真实工作簿自动化业务压测器尚未提供。

`mirror` 指协同引擎：默认演示页面也使用真实 SpreadJS 控件，但同步走自定义协议；官方页面配合 `--impl=real` 才走官方协同链路。上述 `bench` 使用 Node 模拟客户端，不运行浏览器工作簿。

售前、售后可据实验结果与客户共同收敛候选。最终还需用目标官方版本、脱敏业务工作簿、真实操作及计划中的持久化和历史链路，验证持续运行、集中重连与指定故障后的表现。本仓库尚无生产 PostgreSQL 适配器，跨主机 `shared` 共享存储未实现。硬件结论应保留版本、负载、环境及通过条件，让后续扩容有可比较的依据。统一适用边界见[使用边界与免责声明](../DISCLAIMER.md)。
