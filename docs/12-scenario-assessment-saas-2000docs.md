# 场景容量账：2 000 份文档 × 2 人 × 每 2 秒一次增量保存

这是一份**可复核计算和候选验证方案**，不是已通过生产验收的采购单。需要把其他业务交给 AI 评估时，先用[咨询输入模板](13-ai-hardware-sizing.md)。本页没有重新开展压测；旧 mirror 测试、历史广播系数与独立教学假设分别列出。

使用本页硬件候选时，应同时阅读[使用边界与免责声明](../DISCLAIMER.md)；配置取值不能脱离下列输入和假设单独引用。

本页用于演示如何计算容量账。mirror 结果只用于框架验证，不能折算官方容量。硬件评估必须使用真实 SpreadJS 官方协同链路、业务工作簿、操作负载与目标存储链路实测。当前尚未测得官方峰值工作集H；§3的H数值仅为独立、任意的教学假设，不能据此推荐硬件。

## 1. 输入、单位与证据

| 输入 | 本例取值 | 状态 |
|---|---|---|
| 在线文档/房间 | 2 000，每份2人，每人1个会话 | 场景输入；共4 000会话，多标签和重连另计 |
| 文档规模 | 1万/10万/50万有效格，占60%/35%/5% | 场景输入；即1 200/700/100份 |
| 操作频率 | 每人每2秒一次 | 场景输入；本例按一次单格增量op解释 |
| 目标环境 | SaaS、多租户、生产高可用、服务端持久化、历史恢复 | 需求；具体SLO/RPO/RTO须确认 |
| 故障范围 | 丢失一个AZ，3 AZ均匀部署；故障期间不再同时停另一节点 | 本例候选配置的假设边界 |
| 历史策略 | 每份文档每5分钟全量快照，全部保留90天；op热保留7天、归档总保留90天 | 用来核算的明确假设，不是默认产品能力 |
| op载荷 | 未压缩0.2–2 KB/op；压缩归档约100–300 B/op | 独立的工程假设，必须按真实操作校准 |

容量使用十进制KB/MB/GB/TB，机器内存用GiB（1 GiB=2^30 B）。保留90天指包含最近7天在内的总历史范围；若另要求“7天热+再归档90天”，应按97天重算。

“每2秒保存”必须确认。若是整本上传，仅在§4的教学输入“全套JSON为2.5608 GB”成立时，平均每份快照约1.2804 MB，每秒2 000次全量保存约**2.5608 GB/s（20.49 Gbps）**。这不是官方工作簿实测流量；真实上传量须用官方样本体积重算，不能套用增量场景。

证据分为五类：**确定计算、历史/演示实测、工程假设、候选硬件、待验证**。当前官方版本容量、生产PostgreSQL接入、真实跨主机/TLS/HA均未由本页验证。`mirror`只保存简化单元格值，不覆盖官方OT、公式、样式和复杂工作簿。

## 2. 确定的业务量与广播模型

```text
会话 = 2 000 × 2 = 4 000
有效格 = 1 200×10 000 + 700×100 000 + 100×500 000 = 132 000 000
编辑率 = 4 000 / 2 = 2 000 op/s
对端投递率 = 2 000 × (2-1) = 2 000次/s
历史广播模型核数 = 2 000 / 12 700 ≈ 0.1575核
presence历史系数下 = 0.1575×1.17 ≈ 0.1843核
```

前四项由输入确定，后两项只是[历史广播模型](05-performance.md#5-容量模型怎么理解)。它未包含基础编辑处理、OT、序列化、TLS、持久化、快照、GC、复杂工作簿运算及故障恢复。**不能据此断言CPU不是问题，也不能把0.16核作为整套系统需求。** 光标频率不同，应独立测量presence。

## 3. 内存账与故障后的节点容量

### 3.1 官方实测输入与教学假设

硬件评估中的H应来自真实官方协同链路：同时装载全部2 000份目标工作簿、4 000个会话与目标操作负载，接入目标持久化和历史链路，覆盖长时间运行、快照并发、重连及故障恢复，测得协同进程的峰值工作集。H应包含工作簿状态、连接、编辑处理、历史、快照和GC等占用；报告须注明各进程RSS、堆/非堆、采样窗口及聚合口径。系统、代理等协同进程以外开销在§3.2另留预算，避免重复计入。**当前尚未取得这一实测H。**

为保留§3.2的台数算术例，下面**独立、任意设H=99–148.5 GB**。它不是mirror推导、官方实测或官方状态系数，也不是本场景的估计范围；只能演示公式代入，不能据此推荐硬件。

| 必须同时装载的档位 | 份数 | 有效格总量 |
|---|---:|---:|
| 1万格 | 1 200 | 12 000 000 |
| 10万格 | 700 | 70 000 000 |
| 50万格 | 100 | 50 000 000 |
| 合计 | 2 000 | **132 000 000** |

有效格数本身不足以确定官方内存。50万格文档在8 GiB节点上能容纳多少份，仍取决于真实工作簿内容、全部并发负载与故障约束。空/稀疏房间的连接测试不能代表装载1.32亿格后的内存；§7的旧mirror单文档记录也不能用作官方状态系数。

### 3.2 按存活容量选台数

以下用教学H演示`sharded`的内存算术，假设同一时刻每份文档只有一个节点承载状态。另假设：每节点**20%内存保留给系统、代理等协同进程以外开销**；故障重分配后，最重节点比均值高**20%**，即偏斜系数k=1.2。随机哈希不会自动保证这个偏斜上限，需按文档档位配额、迁移及监控验证。

```text
必须满足：H_GB × 10^9 × k / 存活节点数 ≤ 单节点GiB × 2^30 × 80%
算术候选：6台、3 AZ各2台；丢1 AZ后存活4台
上端最重节点需求 = 148.5×1.2/4 = 44.55 GB ≈ 41.49 GiB
64 GiB节点可用于协同进程的预算 = 64×80% = 51.2 GiB
```

代入任意教学H后，**6×64 GiB**在算术上有内存余量；6×32 GiB在故障后每节点只有25.6 GiB协同进程预算，不能覆盖该假设上端。这不是测得的硬件建议：必须先用官方实测H替换，再验证偏斜和故障条件。原先“90–150 GB集群规划、6×32 GiB且保证单AZ故障”的说法不闭合：故障后总物理内存仅128 GiB，约137.4 GB，尚未扣系统保留。

比较其他配置必须重算。4×64 GiB是256 GiB，6×32 GiB是192 GiB，并非总内存相同；4台的AZ分布、最大损失台数和偏斜也不同。`shared`若在多个节点保留同文档副本，还须加入状态复制倍数，本例内存账不能直接照搬。

## 4. 磁盘、快照与90天历史账

### 4.1 快照

实际评估应测量真实官方工作簿在目标存储与传输格式下的快照体积，不能使用mirror每格JSON密度外推。为演示保留策略和带宽算术，下面直接设**每套2 000份快照的JSON为2.5608 GB、压缩后为0.9 GB**，两者都是教学输入，不是本场景官方快照体积的估计，实际压缩率当前未测：

```text
教学输入：每套JSON = 2.5608 GB（官方实测待填）
教学输入：压缩后一套 = 0.9 GB（官方实测待填）
每天套数 = 86400/300 = 288
日增 = 0.9×288 = 259.2 GB
90天快照 = 259.2×90 = 23 328 GB = 23.328 TB
平均快照上传 = 0.9 GB/300秒 = 3 MB/s
```

快照JSON生成平均约8.536 MB/s，但实际若扎堆生成会有CPU、内存和带宽峰值，需错峰和限并发。若压缩比仅达到JSON的1/2–1/3，每套为0.8536–1.2804 GB，对应90天约22.13–33.19 TB。不能把“压缩0.9 GB”当作不随内容变化的常量。

### 4.2 操作日志、数据库与归档

| 数据 | 假设和计算 | 容量 |
|---|---|---:|
| 未压缩op载荷 | 2 000×0.2–2 KB/op | 0.4–4 MB/s，即34.56–345.6 GB/天 |
| 压缩op归档 | 假设约100–300 B/op，取整为17–52 GB/天 | 90天 **1.53–4.68 TB** |
| 7天热op日志载荷 | 若数据库也按上述压缩后大小保存，17–52×7 | **119–364 GB**，未含数据库开销 |
| 快照+90天op归档 | 23.328 TB + 1.53–4.68 TB | **24.858–28.008 TB** |

归档压缩率不等于数据库行的物理占用。如果PG保存未压缩载荷，7天仅原始op就可能是241.92–2 419.2 GB，必须重算数据盘，不能继续用119–364 GB。

一个可检查的**PG盘候选例**：假设热日志可按上述压缩基线存储，行/索引等放大2倍，当前状态预留3 GB，WAL/临时/维护空间合计暂留100 GB，盘至少30%空闲：

```text
所需盘容量 ≥ (364×2 + 3 + 100)/70% ≈ 1 187 GB
因此每个PG数据副本先选2 TB盘做验证；主备各一份，物理盘合计4 TB
```

2倍放大与100 GB维护空间是假设，应根据真实表结构、WAL留存、复制中断和维护演练替换；备份另外计。旧200 GB起的建议不能覆盖热日志上端。每秒2 000 op若平均4条合并一事务，算术上是500事务/秒，但是否能安全批量、何时ACK、SQL/WAL成本需要实现和测量，500不是已有能力。

对象存储按0.9 GB快照假设及归档上端，再留25%容量余量，为28.008×1.25=**35.01 TB**，可按40 TB滚动容量预算验证；若快照按1/2压缩，则(33.19+4.68)×1.25≈47.34 TB，可按50 TB预算。**这些只含快照与op归档**；PG全备、WAL归档、对象版本副本、跨区副本、增长及请求/流量费用要另计。若保留边界需要额外一套锚定快照，按0.9 GB/套另加。不能再称“对象存储0.5–1 TB/年即可”。这是滚动90天容量，全年费用还取决于写入、生命周期和删除策略。

### 4.3 降低历史成本的条件

若预算不足，明确调整为分层快照保留，并逐层相加。例如仅举算术：最近1天每5分钟、此前6天每小时、此前83天每天一套，共288+144+83=515套，按0.9 GB为463.5 GB快照；90天op归档仍有1.53–4.68 TB，备份另计。较老时间点可能需要回放接近一天的op，恢复SLO必须重新验收。最早可恢复时刻还需要一份不晚于该时刻的锚定快照，边界额外保留一套并计算其容量。

“每5分钟一个快照”不等于只能恢复5分钟粒度；要恢复任意时间/版本，必须保留连续、可去重且可按正确顺序回放的op，以及对应版本兼容的快照。不要把同一份快照/op又作为“历史版本”重复加一笔，也不要漏算对象存储自动版本化产生的额外副本。

## 5. 网络、打开与重连账

4 000个会话各自需要初始状态时，每份文档的两位用户各收一份，**不是只传2 000份**：

```text
全会话JSON总量 = 2.5608×2 = 5.1216 GB
按0.9 GB/套的压缩假设，全会话传输 = 1.8 GB
所需平均载荷带宽 = 总传输GB×8 / 完成窗口秒数
```

| 全量打开/重连完成窗口 | 按JSON未压缩 | 按压缩1.8 GB |
|---|---:|---:|
| 5秒 | 8.195 Gbps | 2.88 Gbps |
| 30秒 | 1.366 Gbps | 0.48 Gbps |
| 120秒 | 0.341 Gbps | 0.12 Gbps |

这是整个入口的平均载荷下界，尚未计协议/TLS开销、ACK、presence、重试、突发及节点分布。跨AZ复制、Redis、对象存储与备份在各自链路另算。增量编辑上行约0.4–4 MB/s，对端广播下行另约0.4–4 MB/s，不能只列一份即当作全部流量。

候选可从10 Gbps内网能力开始演练；公网/LB若目标5秒完成全量重连，按压缩假设至少需2.88 Gbps载荷，初选5 Gbps有效入口并测试，压缩不成立时重算。若业务允许120秒恢复，带宽候选可以降低。**没有重连窗口和实测压缩率，不能断言“网络远低于1 Gbps”。**

旧mirror单份50万格加入2.0–2.5秒是同机观察，未测从PG恢复、真实跨AZ、公式工作簿、浏览器渲染或全体重连；不能改写成生产重连2–5秒的承诺。

## 6. 候选硬件清单与架构边界

下表用于演示候选方案的验证清单，不是测得的硬件建议。协同节点的台数和内存只在§3任意教学H下算术闭合，不能据此推荐或采购；须以真实官方链路的实测H重新选择。存储按§4独立假设计算，CPU与IOPS尚没有完整目标场景的实测支撑。

| 组件 | 候选规格/数量 | 通过条件 |
|---|---|---|
| 协同节点 | **6×4 vCPU/64 GiB**，仅为教学H下的算术候选；3 AZ各2台，每台100 GB SSD应用盘 | 先用官方完整状态与负载实测H替换教学值，重新选择台数/内存并测CPU/堆/GC；单AZ故障后偏斜≤1.2且满足§3公式；应用盘按日志保留重算 |
| 入口 | 托管多AZ ALB；自建则2×2 vCPU/4 GiB、50 GB SSD | 按roomId路由，TLS/WebSocket、健康检查与排空；吞吐按§5窗口验证 |
| PostgreSQL | 主备各**8 vCPU/32 GiB、2 TB NVMe**；5000 IOPS仅作初始试验档 | §4.2物理占用假设成立；测批量提交、WAL、锁、复制延迟、故障切换和维护峰值 |
| 对象存储 | 快照+op按**40–50 TB滚动90天预算**，备份/WAL等另计 | 压缩率、完整保留/分层策略及生命周期经复核 |
| Redis | sharded可不需要；shared可选托管HA，或3×2 vCPU/4 GiB的跨AZ自建候选 | 自建应明确数据副本、至少3个独立故障域的Sentinel投票者、自动切换及持久化配置；磁盘按是否持久化另算 |
| 网络 | 内网10 Gbps能力为候选；公网/LB随重连窗口计算 | 同时验证每节点、PG、入口及跨AZ链路；不能只看网卡标称值 |
| 压测生成器 | 独立3–4×2 vCPU/4 GiB起，仅用于mirror初试 | 以稳态目标速率和生成侧监控验收；官方浏览器负载需另行定规格 |
| 观测/管理 | 托管服务或独立容量预算 | 日志量、指标保留、鉴权和管理面隔离另定，不能算作零成本 |

本表“6台协同节点”指6台主机各运行1个协同进程；本仓库其他页面的“节点”通常指进程。Node/V8的默认堆上限未必允许使用整台64 GiB内存，必须按状态预算配置并验证堆/容器限制，监控RSS、非堆内存与GC；若每台主机改为多进程，要同时按每进程和每主机重新检查上限、文档归属和偏斜，不能仅增加进程数便认为拥有更多物理内存。

采用托管ALB、无Redis的sharded方案，基础数据面为6台协同主机+2个PG数据副本；自建网关另加2台，选shared另加Redis。自建PG的故障检测/仲裁、防双主、备份及监控控制面还需明确，不能把“两台PG”当作完整HA实现。

sharded适合作为本例的架构起点，因为每文档只有两人，可把文档分散；但房间数均匀不代表格数/内存均匀。节点失效或路由调整时，需要一致的房间归属、旧节点隔离、数据重载及客户端追平，不能让新旧节点同时写同一份文档。shared可分摊同房间连接和发送，但仍有文档状态、存储并发和总扇出成本，并不自动变成无状态服务。

**本仓库没有生产PostgreSQL适配器或一键切换参数。** 默认sharded的local store是内存，重启会丢；shared使用本机SQLite，真实跨主机shared会被拒绝。要实现上表生产方案，先开发/接入持久化、历史恢复和HA能力，详见[生产说明](06-production.md)和[多机边界](09-multi-machine.md#2-当前支持范围)。开发环境可从2 vCPU/8 GiB起，只做功能验证；两节点预发可做1/3负载回归，但既不是6台生产的“数量减半”，也不能替代3 AZ故障验收。

### 增长时重新算什么

| 改变 | 确定的变化及后续动作 |
|---|---|
| 文档2 000→5 000，规模分布不变 | 有效格与编辑率×2.5；快照/op存储在内容和单op大小等条件不变时重算；同时装载新规模重新测官方H，不能假定内存线性或直接承诺6→10 |
| 每人间隔2秒→0.5秒 | 编辑、投递、op存储×4；重新测CPU与数据库，不再断言每节点小于1核 |
| 每文档人数2→20，每人频率不变 | 用户/编辑×10，每次扇出×19，**总投递×190**，从2 000→380 000/s；presence、连接与数据库另算 |
| 额外增加100份50万格文档 | 额外5 000万格；在官方链路同时装载新增工作簿及负载，重新测H并代入故障公式，不能由格数推算新增内存；若替换原文档则先扣旧格数 |

## 7. 旧测试记录：能说明什么

以下保留2026-10-28旧mirror记录供追踪，**本次未重测，原始报告未随本文附上**。记录环境为Windows、22核、Node24，同机同时运行服务端与生成器，可能发生资源争用，不能简单称“数字偏乐观”。

| 旧场景 | 旧报告op/s | CPU/ACK记录 | 限制 |
|---|---:|---|---|
| A：4 000连接/2 000房间/每2秒，15秒参数 | 905 | 0.33核，ACK p95 707 ms，RSS峰303 MB/空闲后82 MB | 旧总窗口包含建连，不能与稳态2 000 op/s直接比较 |
| B：500连接/500房间/每50 ms，20秒参数 | 5 512 | 0.58核，ACK p95 61 ms | 同上；稀疏文档，与目标1.32亿格不同 |
| C：200连接/100房间/每100 ms，20秒参数 | 1 738 | 0.25核，ACK p95 31 ms | 同上；不是4 000连接完整场景 |

这些数字**不能证明单进程在4 000连接时只能发905 op/s、生成器饱和或ACK排队在客户端**。必须分开建连/加入窗口与稳态写入窗口，记录成功操作数、实际计划速率及生成器/服务器/存储监控后定位；旧吞吐须重测。旧场景压测也未同时装载2 000份目标规模文档，不能把它与单文档内存试验拼成完整场景验收。

单文档50万值单元格的旧观察为：写入约46–47秒，报告10 600–10 800 op/s（批并发200）；RSS约71 MB起，写入后206–314 MB，空闲后136–138 MB；第二客户端收到50万格约2.0–2.5秒；JSON约9.3–9.7 MB。稳态增量约65–67 MB，即约130–134 B/格。不同试验基线与GC时刻不完全一致，不宜把峰值B/格当精确上界；这些数值不能用作官方状态系数，JSON19.4 B/格也仅是该mirror值内容的密度。旧“压缩后2–4 MB”缺少本文可复核的线字节证据，本页仅把0.9 GB/套当规划假设。

## 8. 持久化、RPO/RTO与验证门槛

持久化路径候选为“追加有序op+周期快照”。若允许异步ACK，必须明确已经确认但尚未耐久的编辑可能丢失及其窗口；RPO为0时应在满足目标复制/耐久条件后ACK，并重新测延迟。快照周期不自动决定RPO，操作日志完整性、WAL归档与故障范围共同决定。单文档历史回放、PG整库PITR、区域灾难恢复也是不同操作，不能共用未测RTO。

本页可提出的**待确认验收目标**示例为：成功率≥99.9%、ACK p95<300 ms、广播p95<500 ms、24小时内存无持续增长；全量重连采用§5的明确窗口；单AZ故障后仍满足同一SLO。CPU<60%可作余量观察项，但不能替代延迟、队列和数据正确性。用户仍需指定已确认编辑RPO、单文档与整库RTO；未经演练不承诺秒级或分钟级恢复。

验证按以下顺序进行：

1. 先用mirror小规模`check`验证拓扑行为。`healthy`不代表性能通过。
2. 负载生成先完成建连/加入，再统计稳态写入窗口。原始报告同时记录建连时间、稳态成功op数和持续时间、总窗口、各参与者时钟/样本及组件监控。需要多机时按[多机手册](09-multi-machine.md)部署；现有自动验证是同机进程模拟，真实跨主机仍需验收。
3. 同时准备全部2 000份目标规模、真实公式/样式的工作簿，打4 000会话、2 000 op/s及真实presence，覆盖长时间运行、快照并发和历史写入。不能只放一份大文档或短跑60秒就作为生产容量结论。
4. 当前`bench`仅支持mirror，不能用它验收官方OT容量。官方版本要另建实际浏览器/SDK负载方案并校验成功率、收件与正确性，见[官方实现说明](07-license.md)。
5. 演练单节点、单AZ、PG主备切换、Redis故障（若采用）、全量重连、发布排空、历史中间版本恢复与整库PITR；记录丢失/重复编辑、恢复窗口及故障后最重节点资源。
6. 测得上述全量状态、业务负载和目标存储链路下的官方峰值工作集H，并测量数据库实际字节/op、WAL与备份增长、压缩快照体积和对象版本生命周期，替换§3–§5的假设，重新计算候选规格，最后再给采购与扩容阈值。

下面仅是mirror多机负载命令示意，不能实现PG生产方案，也不证明真实跨主机容量。PowerShell使用反引号续行；先按多机手册在g1/g2启动agent并配置token/可达地址：

```powershell
npm run up -- --mode=sharded --nodes=1 --agents=http://g1:9100,http://g2:9100 --agent-token=TOKEN_VALUE
npm run bench -- --users=4000 --interval=2 --duration=60 --rooms=2000 `
  --distribute=local,http://g1:9100,http://g2:9100
npm run down -- --stop-agents
```

此处意图是1个本地节点+2个agent节点，主控仍需保留LB。主机名、地址、端口和安全配置按实际环境替换；节点与生成器同机时分别监控资源。测试报告需保存原始时间窗，60秒命令只用于初试。
