## 按 Windows 演示用途补齐

- 首页、入门与开发说明统一以 Windows + PowerShell 为主，其他系统标注未验证。
- 场景参数只在缺省时使用默认值；CLI / API / 页面拒绝非法数值，capacity 检查房间数与节点核数。

## 实验后续改进与生产前置条件

以下问题尚未处理。当前仓库以受控的 Windows 演示为主；若用于生产，完整管理鉴权、凭据保护与异常恢复必须在上线前解决。分享日志前仍需留意凭据。这些限制不能用[免责声明](../DISCLAIMER.md)代替修复或验证。

### 1. 管理接口需要统一访问控制

[src/web/server.mjs](../src/web/server.mjs) 的启停和负载接口没有完整鉴权；[hub.mjs](../src/server/hub.mjs) 以及负载均衡还提供状态和停止接口。agent 与动态 upstream 管理的 token 只覆盖部分接口。

跨机将 bindHost 改成 0.0.0.0 后，其他可达主机可能读取状态或停止节点。仅绑定 loopback 也不能替代网页请求的 Origin 校验。

建议：管理面单独监听或统一鉴权，浏览器写操作校验 Origin / CSRF；负载任务限制并发；公开网络只转发协同业务路径。当前文档按受控实验环境定位，未宣称可以直接公开部署。

### 2. 带凭据的连接 URL 还没有统一脱敏

[src/lab/redis.mjs](../src/lab/redis.mjs)、[node-server.mjs](../src/server/node-server.mjs) 及部分状态 / 报告会带 Redis URL。默认地址没有密码，一旦配置 redis://user:password@host，就可能将凭据带入日志或分享的报告。

本轮只处理了管理 token 字段。建议后续统一生成可公开的 URL（移除 userinfo），错误、报告、CLI 和控制台共用这套处理，并用带凭据的配置回归验证。

### 3. 启动、清理和异常恢复还要加固

[orchestrator.mjs](../src/lab/orchestrator.mjs) 注释称节点串行启动，实际先启动所有节点，再逐个等待健康；对于共享 SQLite，启动竞态仍需关注。down 主要按 PID 和端口识别进程，长期遗留的状态还存在 PID 被复用的风险。

节点和 agent 的未捕获异常处理只记录、继续运行，也可能留下部分失效状态。建议用运行实例标识校验归属，统一有界回滚，明确异常后停止与重启策略，并覆盖启动中断、状态损坏和重复启停场景。

### 4. 负载统计需要更明确的可验证含义

[bench.mjs](../src/bench/bench.mjs) 的 fan-out 由成功操作数和成员数推算，不是完整消息收件计数。分布式延迟聚合使用参与者分位数的最大值，也不是全局原始样本分位数。

文档已解释这两点。建议报告字段进一步标记 estimated / observed，记录端到端丢失或重复数；若要报告全局 p95，应合并直方图或原始样本，而非直接合并分位数。

## 发布与维护建议

- 将本目录作为独立仓库根目录发布。本轮没有创建远端仓库或推送。
- 新增锁文件后，安装依赖优先使用 npm ci。保留 private:true 可以防止误发到 npm，不影响 GitHub 开源。
- 在对应系统完成验证后，再标注 Windows / macOS / Linux 支持状态；当前机器只直接验证 Windows。
- 对历史性能数据，补发脱敏原始产物与复现脚本，或继续作为历史参考。没有公开原始证据前，不建议写成当前版本的 benchmark 宣传。
- Node 最低声明仍是 >=20，但浏览器脚本使用全局 WebSocket，旧版本兼容性应单独验证；目前指南推荐 22 / 24 LTS。
- 当前演示定位无需扩展 PostgreSQL。若后续需要验证真实跨机的共享房间，再补充共享存储接口及对应故障、并发写入测试，完成前不要宣称支持。
